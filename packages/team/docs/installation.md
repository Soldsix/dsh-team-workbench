# 安装、升级与回滚

## 概要

普通用户安装发行包，不必构建源码。已有 DSH 自定义配置时使用安装助手迁移提供方设置；所有操作先在独立 home 验证，再由部署者停止目标宿主并切换。插件不携带也不覆盖模式、人设、账号或模型目录。

## 准备与计划

先核对 [SHA-256 清单](../SHA256SUMS)与[兼容矩阵](compatibility.md)。发布包中的 `.tgz` 已包括八个内部模块；这些模块不是需要分别安装的插件。源码 ZIP 用于开发，不能直接当 bundle 根目录安装。

以下参数由部署者填写绝对路径。`--cli` 是当前 DSH 安装的 `lib/bin.js`，`--home` 是准备升级的 DSH home，`--profile` 是目标 profile；助手通过受支持的 `dsh` CLI 管理包，不直接启动底层应用。

```text
node scripts/install.mjs --cli <DSH的lib/bin.js> --home <独立DSH_HOME> --profile web --archive <发行包.tgz>
```

默认生成 `workbench-install-plans/<时间>/`，包括 proposed patch 和计划元数据。目录可能包含原配置中的私有值，应保留在本机，不随漏洞报告上传。助手只迁移 tools、sandbox-policy、subagent、web、web-fetch-http 五行的配置；模型与模式行保持原值。

旧版用户补丁若覆盖了整块 agent-team 配置，助手只补充缺失的 V5 创建、协调与交付选项，保留已显式配置的值，并在计划中列出 addedRuntimeKeys。动态计算的整块配置需要手动迁移；不会在无法解释时悄悄覆盖。

## 安装

确认目标宿主已停止后，在上述命令后增加 `--apply --host-stopped`。助手保留原 profile 文件的字节备份，将原依赖目录移入本机备份，调用 `dsh plugin --profile web add <发行包.tgz>`，原子写入迁移补丁，再检查配置合成。失败时恢复原文件与依赖目录，失败的新依赖另存供检查。它不终止进程，也不重启服务。运行中的任务必须由部署者先处理完毕。

全新 profile 也可直接执行 `dsh plugin --profile web add <发行包.tgz>`。已有自定义配置应使用助手：DSH 补丁的 `name` 是校验条件，不能用来替换实现；原五个提供方必须禁用，由 `workbench-*` ID 的兼容提供方接管。直接保留会重新启用旧提供方的用户补丁会造成冲突。

使用原来的受支持启动方式启动目标 profile。打开 CLI 新打印的浏览器地址；该地址包含登录凭证，不应复制到公开报告。确认插件清单中五个兼容模块和五个团队入口为 active，再建立无害的试验会话。

首次使用只需选择已有模式和模型，提出目标，再要求模型读取 `team_help start`。完整方案需要真实可用的 provider、model、思考档、技能、任务输入与输出、独立复核人和资源预算；缺项会在确认前报出。用户批准确切版本后，程序开始派工。

## 升级和回滚

升级前记录包版本、宿主版本及 profile 备份位置。Session、工作区成果与原模式另行做一致备份；本安装助手只备份其会修改的 profile 文件。旧原生团队事件需要能够识别它们的宿主，不能因为安装了新包就假定旧世代可迁移。

新版本使用已知 Session 事件载体保存团队记录；读取仍需要本插件解释，卸载后不能继续原团队执行。回滚时停止目标宿主，恢复安装助手保存的 profile 原文件及对应旧包依赖；保留升级后新增的 Session 和成果，勿用旧目录覆盖整份数据。包缓存残留不会自动启动服务。

确认不再需要团队运行时，可在隔离副本执行 `dsh plugin --profile web remove @dsh-workbench/team`。先恢复迁移前提供方补丁，再重启核查；不要只删除包而继续保留 `workbench-*` 的用户配置行。正式卸载前应结束团队任务并保存交接。

## 故障定位

创建成员一直等待时，检查当前目标是否确认、完整方案预检、派发诊断消息、模型额度和工作集错误；不要另建一队重复任务。空面板先使用重试恢复投影，状态缺失会显示同步中。使用 `team_help tools` 检查成员实际工具名称，使用 `team_help network` 检查搜索提供方与授权。

报告时附版本、复现步骤、任务编号及“诊断与资源”导出的元数据。不要上传完整 Session、请求正文、模式文件、私有配置、浏览器登录地址或 API 密钥。
