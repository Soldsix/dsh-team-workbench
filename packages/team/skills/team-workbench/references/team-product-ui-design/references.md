# 产品与 UI 设计参考

## 用户任务与信息架构

先选最重要的三到五个用户任务：提出目标、查看并批准方案、理解当前状态、查看证据、处理阻碍或接受交付。每条任务列入口、所需信息、操作、反馈、异常和结束状态；避免先堆功能再找用途。产品名称、权限与角色词汇保持一致。

基础用户看到可执行下一步和清楚状态，专家通过高级入口调模型、思考、资源、技能和并发。默认值要说明依据及实际生效值；模板与当前团队的区别可见，模板为空不代表成员不存在。

## 三栏与分组视图

左栏是成员与层级：主沟通者、规划/质量军师、长期专家、组长和孙代理。行显示角色、实际模型、思考、状态；准备或失败的成员仍可点，长期身份与临时执行状态分开。

中栏是分组任务：按工作组或状态组织，显示 owner、reviewer、依赖、验收进度和等待原因。重要未处理决定集中，不能让用户穿过几十张成员卡才看到卡点。大团队按组折叠、筛选与搜索，保留选中项。

右栏是所选成员/任务的详情：模型与待切换值、技能版本、目标、执行、成果、证据、记忆和恢复动作。顶部完整方案可打开全部成员与阶段，确认绑定版本；不能用截断预览作为唯一审核内容。

窄屏改为导航与单一详情而非强行挤三栏；键盘和返回路径清楚。复用现有设计 tokens，间距、文本层级、边框与背景承担层次。不要把 every item 做成巨型彩色卡，也不要靠营销渐变隐藏信息密度问题。

## 状态与反馈表

| 状态 | 应显示 | 操作 |
|---|---|---|
| 初始空态 | 没有团队/任务的原因和起点 | 建立目标或查看方案 |
| 准备 | 哪个步骤在进行、耗时与失败 | 看准备详情/取消 |
| 运行 | 实际任务和阶段 | 看会话、产物与进度 |
| 待命 | 无可执行工作或等待条件 | 查看依赖/技能/额度 |
| 待复核 | 已提交证据、复核员 | 查看并复核正确版本 |
| 冷却 | 原错误、恢复条件与时间 | 换已允许连接或等待 |
| 缓存/断连 | 最后可用内容、更新时间与具体失败 | 重试恢复，不清空已显示内容 |
| 失败 | 失败步骤、影响、保留成果 | 恢复/修改配置/查看证据 |

toast 用于短暂操作反馈，持续阻碍放在对应区域；错误不能只在日志里出现。相同错误集中显示，用户可以读完整内容。颜色之外加文字/图标，屏幕阅读器能识别状态变化。

## 可访问性与性能

按 [WCAG 2.2](https://www.w3.org/TR/WCAG22/) 的相关标准核对键盘、焦点、对比度、缩放与点击目标；触控更宽松的目标可以改善体验，具体数值与例外查原标准，不能把增强等级冒充最低要求。弹窗关闭后焦点返回触发处，滚动容器不困住键盘。

用 8/20/32 成员和长任务列表测试。共享投影单点订阅、按需详情、稳定键值与减少无关重渲染；只有真实测量证明瓶颈才加虚拟化或缓存。记录机器、数据量、版本、指标与改进幅度，不把主观“更快”当性能验收。

## 交付清单

流程图、信息结构、布局/原型、状态文案、组件与 token 说明、数据来源、异常交互、可访问性、性能测量和逐项验收。GUI 演示必须是真实服务器与业务流程；静态图片只说明设计，不能证明授权、成员创建或任务恢复成功。
